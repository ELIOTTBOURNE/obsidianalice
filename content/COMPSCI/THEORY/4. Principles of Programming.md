#### **1. Procedural Programming**

- **Nature**: Linear execution of instructions (sequences, loops, functions).
- **Advantages**: Simple, predictable flow.
- **Uses**: Scripting, mathematical computations (e.g., C, Python).

#### **2. Object-Oriented Programming (OOP)**

- **Nature**: Organises code into **objects** (data + methods).
- **Advantages**: Modularity, reusability (via inheritance), encapsulation.
- **Uses**: GUI applications, large-scale systems (e.g., Java, C++).

#### **3. Event-Driven Programming**

- **Nature**: Responds to events (clicks, timers).
- **Advantages**: Responsive user interfaces.
- **Uses**: Web apps, games (e.g., JavaScript, Python with Pygame).

#### **4. Visual Programming**

- **Nature**: Drag-and-drop blocks to create logic.
- **Advantages**: Accessible for beginners.
- **Uses**: Education (e.g., Scratch), IoT workflows.

#### **5. Markup Languages**

- **Nature**: Annotates text with tags for structure.
- **Advantages**: Human-readable, platform-agnostic.
- **Uses**: Web development (HTML), data serialisation (XML).

### **Object-Oriented Approach**

#### **Key Concepts**

|**Term**|**Definition**|**Example**|
|---|---|---|
|**Class**|Blueprint for objects.|`class Car { ... }`|
|**Object**|Instance of a class.|`Car ford = new Car();`|
|**Method**|Function defined within a class.|`ford.accelerate();`|
|**Attribute**|Data stored in an object.|`ford.colour = "red";`|

#### **Relationships**

- **Class → Object**: A class defines structure; objects are concrete instances.
- **Object → Method**: Objects invoke methods to perform actions.

### **Standardisation of Programming Languages**

#### **Why Standardise?**

1. **Portability**: Code runs across platforms (e.g., Python on Windows/Linux).
2. **Maintenance**: Easier to update/expand code written to standards.
3. **Interoperability**: Libraries/tools work together (e.g., HTML5 across browsers).

#### **Challenges**

- **Bias**: Vendors may push proprietary extensions (e.g., Internet Explorer’s legacy HTML).
- **Ambiguity**: Natural-language documentation can lead to misinterpretations.
- **Adoption**: Slow consensus among stakeholders (e.g., C++ standards committee).

### **Ambiguity in Natural Language vs. Programming Syntax**

|**Natural Language**|**Programming Language**|
|---|---|
|"Close the door." – Which door?|`door.close()` – Explicit object reference.|
|"He saw her with binoculars." – Ambiguous modifier.|`binoculars.observe(person)` – Unambiguous method call.|

**Need for Unambiguous Syntax**: Prevents errors (e.g., `3 + 5 * 2` always evaluates to `13`, not `16`, due to operator precedence rules).

### **Formal Syntax Methods**

#### **1. Backus-Naur Form (BNF)**

- **Purpose**: Define grammar rules rigorously.
- **Example**: Validating integers:
    

bnf

- ```
    <digit> ::= 0 | 1 | 2 | ... | 9  
    <integer> ::= <digit> | <digit><integer>  // Recursion for multi-digit numbers  
    ```
    
- **Interpretation**: `42` is valid: `4` → `<digit>`, `2` → `<digit><integer>`.

#### **2. Syntax Diagrams**

- **Components**:
    - **Oval**: Terminal symbol (e.g., `+`, `if`).
    - **Rectangle**: Non-terminal (e.g., `<expression>`).
    - **Arrows**: Flow of syntax rules.
- **Example**:

- ```
    (Start) → [<digit>] → [<integer>] → (End)  
               ↑_____________|                // Recursive loop  
    ```

### **Key Comparisons**

#### **High-Level vs. Low-Level Languages**

|**Aspect**|**High-Level (Python)**|**Low-Level (Assembly)**|
|---|---|---|
|**Abstraction**|Hides hardware details.|Direct memory/CPU access.|
|**Readability**|Human-friendly.|Machine-friendly (opcodes).|
|**Use Case**|Web apps, data science.|Firmware, device drivers.|

#### **BNF vs. Syntax Diagrams**

|**Method**|**Pros**|**Cons**|
|---|---|---|
|**BNF**|Precise, compact.|Less visual.|
|**Syntax Diagrams**|Intuitive for visual learners.|Complex for large grammars.|
